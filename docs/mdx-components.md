# MDX component library and the Cloudinary image loader

The five React components that replace the Hugo shortcodes, plus the responsive-image
pipeline they depend on. Everything here lives under `web/`.

## The prop contract is fixed

`web/scripts/lib/shortcodes.ts` (`REGISTRY`) is the authority on component names and prop
names — the migration derived them from the Hugo templates, and 170 already-migrated content
files call these components with exactly those names. Renaming a prop breaks the whole corpus
at once.

| Component | Kind | Props |
|---|---|---|
| `ImageModal` | self-closing | `src, alt, caption, width, height, title, buttonUrl, buttonText, srcSet, variant` |
| `NavButton` | self-closing | `url, text, direction, className` |
| `BeforeAfter` | self-closing | `before, after, altBefore, altAfter, captionBefore, captionAfter, mainCaption, width` |
| `Gallery` | paired | children only |
| `FlexImages` | paired | `className, style` |

**Every prop value is a string.** The migration emits JSX expressions carrying the Hugo
parameter verbatim (`width={"500px"}`), so `width`/`height` are CSS lengths, not pixel counts,
and never reach `next/image` as dimensions. `FlexImages`' `style` arrives as a raw CSS
declaration string and is parsed into an object.

## Images: loader + dimension manifest

Two separate pieces solve two separate problems.

**`lib/cloudinary-loader.ts`** — wired as `images.loader: 'custom'` in `next.config.ts`.
`output: 'export'` removes the built-in optimizer, so without this every image is served as
authored, and all 272 distinct Cloudinary URLs in the corpus are bare
`/upload/v<version>/<name>.jpg` with no transformation segment: a phone downloaded the same
full-size JPEG a desktop did, with no srcset to choose from. The loader injects
`f_auto,q_auto,w_<width>,c_limit` after `/upload/`. `c_limit` never upscales. Non-Cloudinary
sources — local `/img/*` and three third-party editorial images — pass through untouched.

**`lib/image-dimensions.json`** — generated by `npm run images:dimensions`, committed, read
through `lib/image-dimensions.ts`. `next/image` needs real dimensions to reserve a box, and
content cannot supply them: `width` is a CSS string with no aspect ratio, and `height` appears
on 6 images out of ~490. The script resolves Cloudinary dimensions via `fl_getinfo` (a few
hundred bytes per URL instead of the whole image) and everything else with `image-size`.
Re-run it when content adds images; a missing entry degrades to an unsized image rather than
failing the build.

`sizes` differs by context, which is why `Gallery` publishes membership through
`gallery-context.tsx` rather than the components inferring it. Note the obvious inference is
wrong: 221 of the 295 in-gallery images declare a `width` prop (it is simply inert there,
overridden by the cell), so presence of `width` says nothing about whether an image is in a
gallery.

### `sizes` in a gallery describes the crop, not the cell

A gallery cell is a fixed-ratio box — `4 / 5`, or `16 / 9` for `variant="wide"` — and the image
fills it with `object-fit: cover`. Covering scales the image until *both* axes reach the box,
so an image wider than its cell is scaled up until its height fits and then cropped left and
right. The painted width is `cellWidth × (imageAspect / cellAspect)`, not `cellWidth`.

`sizes` describes the box, so the uncorrected `33vw` under-stated the request by that same
factor and the browser fetched a candidate several stops too small. The crop then upscaled it.
This is invisible on the images the cell crops *vertically* (a portrait in a portrait cell,
factor 1) and gets worse the wider the image gets: a sweep of all 295 in-gallery images found
**91 blurry at a 1920 viewport, the worst at 2.0×** — 2.7:1 panoramas in 4/5 cells fetching the
640px candidate to paint 1275px.

`coverFactor()` in `ImageModal.tsx` reads the aspect ratio out of the dimension manifest and
`scaleSizes()` multiplies every entry of the `sizes` list by it. An image missing from the
manifest gets a factor of 1, which is the pre-existing behaviour.

Two consequences worth knowing:

- **`deviceSizes` had to grow back to 2560/3840.** It had been trimmed to 1920 on the premise
  that nothing renders wider than the 1170px container; a cover crop breaks that premise. The
  entries only cost two srcset items, since `sizes` still governs selection.
- **8 images stay soft and no `sizes` value can fix them.** They are 1350×498-ish panoramas in
  `wide` cells: covering a 16/9 cell needs 1737px and the Cloudinary *original* is 1350px wide
  (verified against the untransformed URL — `c_limit` has nothing larger to return). Only a
  higher-resolution re-upload, or a cell ratio closer to the image, removes the 1.29× upscale.

Measure it in the browser rather than reasoning about it, and note that `naturalWidth` is **not**
the bitmap's pixel width when a `w`-descriptor srcset is in play: it is the bitmap divided by
its density, and density is `descriptor / sizes`. The descriptor lies whenever `c_limit` clamps
— next/image labels the `w_1920` URL `1920w` and Cloudinary returns the 1350px original
untouched. Compare against `Math.min(candidateWidth, manifestWidth)` instead.

## The modal

One modal instance per page, reproducing Hugo's `Scratch`-flag dedupe of `#imageModal`.

- **Election** (`image-modal/use-modal-host.ts`) — the first `ImageModal` to subscribe claims
  the host role and renders `ModalHost`; everything else renders nothing. Done through
  `useSyncExternalStore`'s `subscribe`, not a `setState` in an effect, so only the instance
  whose answer changes re-renders. The contract is "exactly one", not "the first one".
- **State** (`image-modal/store.ts`) — a module-level store, because the images that can open
  the modal share no common React ancestor and mounting a provider would mean owning the page
  layout. One subscriber, so opening or navigating never re-renders the other images.
- **Scoping** — which images are navigable siblings is read from the DOM at click time via
  `closest('[data-gallery-root]')`, exactly as the Hugo JS did with `.photo-gallery`. The DOM
  already states document order; reconstructing it from mount order would be strictly worse.
- **Phases** — `closed → opening → open → closing → closed`. `opening` holds for one painted
  frame (double `requestAnimationFrame`) so the opacity transition has a start value; this
  replaces the source's `offsetHeight` reflow read. `closing` has a timeout backstop because
  `transitionend` does not fire when the tab is backgrounded mid-transition, when the
  transition is interrupted, or under `prefers-reduced-motion` — without it the modal sticks
  in `closing`, visually gone but still exposed to assistive technology.

The `ImageObject` JSON-LD is **not** emitted by the modal. `findFirstImageModal` walks the
compiled MDX element tree during the server render, so the script lands in the exported HTML;
a client-side "first to mount wins" flag would only add it after hydration, where a crawler is
unlikely to see it.

## Bugs fixed in the port, not carried across

1. **`target="_blank"` on internal links.** Both `navbutton.html:28` and `image-modal.html:19`
   forced it unconditionally, so every "contact me" and gallery CTA abandoned the current tab.
   Now external-only, via `lib/links.ts`.
2. **`NavButton` direction labels were never translated.** `navbutton.html:11-19` reads
   `.Get "text"` from inside `{{ with .Page.PrevInSection }}`, where the dot has been rebound
   to the target page — so the shortcode's own parameter is unreachable and a hardcoded
   English default always won, on French pages too. Labels now resolve through next-intl.
   Only the label half is fixed: the URL came from `.Page.PrevInSection`, and section ordering
   is a page-layer concern, so `url` remains required. No content uses `direction`.
3. **`BeforeAfter` re-emitted its entire `<style>` and `<script>` per invocation**, so the
   restoration page shipped four copies of both and bound four duplicate listener sets. Styles
   are now a CSS module and behaviour is component state.
4. **Modal aria-labels were hardcoded English for both locales** (`image-modal.html:28-31`).
   Now translated — the French strings are new, not ported.

Deliberately **not** fixed: `before-after`'s `.image-comparison::before` gradient is pinned at
50% and does not follow the handle. Reproducing current appearance is the rule; changing it
would be a design decision.

## Styling

CSS Modules for the components whose rules are deeply descendant-scoped (gallery, modal,
before/after), Tailwind for the simple ones. `gallery.module.css` is shared by `Gallery` and
`ImageModal` deliberately: the source styles the figure through selectors rooted at
`.photo-gallery`, so both must resolve to the same generated class names — two modules would
hash them separately and the descendant rules would never match.

Two variants that depend on a page-level `.dark-gallery` class are **not** ported, because that
class is owned by the page-layout work: `.dark-gallery .flex-images .nav-button` and
`.dark-blog .flex-images img`. The gallery-overlay button variant *is* ported, since the
gallery half of its selector is knowable here.

## i18n

next-intl is wired through `components/intl-provider.tsx` with explicit `locale` and `messages`
props — no plugin, no `i18n/request.ts`, no middleware.

**next-intl's routing module is permanently unusable on this site**, and not only because
static export disables middleware: under `output: 'export'` it forces `localePrefix: 'always'`,
while this site's contract (`lib/permalink.ts`) gives French no prefix at all. Route groups
with a hardcoded locale each are the only viable shape. Do not reach for `defineRouting`,
`createNavigation`, or a `[locale]` segment.

`intl-provider.tsx` must stay a **client** component. Imported from a server component,
`NextIntlClientProvider` resolves through the `react-server` export condition to a variant that
fills in absent props by reading the request config — it calls `getFormats()` and
`getConfigNow()` unconditionally — and the build fails with "Couldn't find next-intl config
file" even when locale and messages are both supplied.

Item #5 landed those route groups: `IntlProvider` now sits in `app/(fr)/layout.tsx` and
`app/(en)/en/layout.tsx` (via `lib/pages/site-layout.tsx`), and no `useTranslations` call site
changed. Note the English path — the group alone does not produce the `/en` prefix.

Server components cannot use `useTranslations`, and `next-intl/server` is unusable here for
the same missing-config-file reason described above; `lib/translate.ts`'s `getT(locale, ns)`
is the server-side equivalent. See `docs/routing-and-chrome.md`.

## Verification surface

`app/preview/[fixture]/` is **dev-only and should be deleted** when real content routing lands.
It compiles four real migrated files through the component map: `portraits` (gallery, `wide`
variant, gallery CTA), `restoration` (three BeforeAfter sliders, standalone image, NavButtons),
`iframe` (raw HTML passthrough), and `portraits-en` (the same gallery in English). It is the
only place `@mdx-js/mdx` is imported by app code rather than by the migration script, which is
why that package can stay a devDependency until the route is gone.
